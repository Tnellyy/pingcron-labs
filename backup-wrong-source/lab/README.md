# A backup can exit 0 and restore the wrong data

A controlled, synthetic SQLite failure lab for the PingCron article. No production databases, credentials, real cloud store, or PingCron API are used. Python standard library only.

## Run

Use Python 3.12 or later with SQLite support, and allow local HTTP connections to 127.0.0.1. Only Windows was tested. Do not interpret this as a production backup implementation.

```console
python lab.py all --output results/my-run --repetitions 3
python test_predicate.py
```

The output directory must not already exist. Each run receives a unique ID and fresh fixture. Individual case example:

```console
python lab.py wrong_source --output results/my-wrong-source --repetitions 1
```

The harness exits 0 when the observed results match the experimental expectations. That does not mean every backup succeeded. Inspect the actual `workflow.process.json` exit and `result.json` stage outcomes. A detected wrong-source backup has exporter exit 0, validator exit 3 and validated wrapper exit 1.

Use your own Python executable for the commands above. Recorded machine-specific executable and project paths in public logs are replaced with [PYTHON] and [LAB_ROOT]. Every child command is recorded per run.

## Predicate and isolation

`fixture.py` writes an independent expected-data specification before building either database. Two related tables hold deterministic logical rows. In repetition 1, the intended database includes transactions 1041 and 1042; the stale database has only 1041. Later repetitions increment the marker. Writes are paused throughout each experiment.

`backup.py` opens the configured source read-only and uses SQLite's backup API, closes both connections, creates a fresh archive with run metadata, then atomically renames it. The working control uses the intended source. The main wrong-source case changes only the configured source path to the stale, same-schema database. It still produces a new artifact for the current run.

`receiver.py` is a separate local HTTP process that stores the upload under a run-specific key. A later verifier process downloads it independently, compares SHA-256 with the uploaded bytes, extracts the database into a new directory, and opens only that restored database. It asserts:

1. Retrieved bytes match the uploaded bytes.
2. Artifact metadata names this run.
3. `PRAGMA integrity_check` returns exactly `[("ok",)]`.
4. `PRAGMA foreign_key_check` returns no violation rows.
5. Sorted accounts and entries equal the independent specification, including the expected transaction and every amount.

A Python audit hook rejects file reads under `sources/` and every SQLite connection except the restored database. Each verifier deliberately tries both a Python file read and a SQLite connection to the original source and records their rejection. This is an accidental-access guard in a cooperative lab process, not an OS-level security sandbox or defense against malicious code.

The complete-row oracle is practical for this tiny fixture. A production recovery target needs its own independently maintained identity, freshness and business-invariant assertions. A manifest generated by the wrongly configured exporter is not independent evidence of the intended source.

## Conditions and actual stage exits

All three repetitions had the following results. `not attempted` is not a success.

| Condition | Exporter | Validator | Validated wrapper | Weak signal | Validated signal |
|---|---:|---:|---:|---|---|
| control | 0 | 0 | 0 | received | received |
| wrong_source | 0 | 3 | 1 | received | not attempted |
| masked_export_failure | 2 | not run | 1 | received | not attempted |
| stale_artifact | 0 | 3 | 1 | received | not attempted |
| corrupt_transfer | 0 | 3 | 1 | received | not attempted |
| lost_object | 0 | 3 | 1 | received | not attempted |
| not_started | no process | no process | no process | not attempted | not attempted |
| checkin_unavailable | 0 | 0 | 0 | HTTP 503 | HTTP 503 |

The weak and validated policies share the same exported/uploaded artifact and injected condition. The weak comparator sends after a successful upload, before restore validation. For the masking case, `weak_wrapper.py` actually starts a failing exporter, records its exit 2, discards that status and returns 0, then the weak comparator sends. These intentionally weak policies are not described as the working baseline.

The validated wrapper's exit represents backup verification. When verification passes but the signal endpoint returns HTTP 503, backup exit remains 0 and delivery failure is recorded independently. An integration may choose a separate process exit for notification failure, but must preserve these distinct outcomes.

The stale-artifact condition creates a deliberately staged previous-run archive from the stale fixture, with a previous-run identifier, then selects it instead of the newly exported artifact. It is not an artifact left on disk since yesterday. The main wrong-source condition does not use that selector bug.

The corruption fault changes a byte after accepting the upload. The receiver acknowledges the received digest, while the later download fails digest comparison. The loss fault stores and removes the object before sending its HTTP 201 acknowledgement; the subsequent GET returns HTTP 404. These are protocol counterexamples against relying on acknowledgement alone, not claims about any provider's durability.

The not-started case deliberately omits the workflow invocation in the local harness. It is not a cron emulator and does not prove a root cause for a missing real-world check-in.

## Limits

This is a small, paused-write SQLite experiment. It does not test concurrent writes, point-in-time recovery, retention, off-site durability, encryption keys, permissions after disaster, production scale, full recovery time objectives or every business invariant. Matching SHA-256 proves equality to the supplied uploaded bytes, not correct source selection or durable future storage. Run metadata can be self-consistent while the data is wrong. A check-in proves receipt of a signal, not backup correctness or automatic repair.

Use a fresh `--output` path for each execution. Keep result directories when auditing a claim. Any manual cleanup should be restricted to the chosen output directory.

Primary method references: https://www.sqlite.org/backup.html and https://www.sqlite.org/pragma.html#pragma_integrity_check.
